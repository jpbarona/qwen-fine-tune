## LFM support and assumptions

The requested model is the instruction model `LiquidAI/LFM2.5-2.6B`, pinned at
`7141b56cd4650af95c7c7b86983443aed050c96a`. The full and smoke profiles are
`configs/lfm.toml` and `configs/lfm-smoke.toml`.

- GRPO, group-normalized advantages, reward arms, the measured pool, test
  execution, judge usage, checkpoint frequency, and evaluation use the shared
  pipeline.
- The starting hyperparameters match Qwen. These are comparison defaults and
  require tuning against the larger model's GPU memory and reward behavior.
- The profile lists LFM attention targets as `self_attn.q_proj`,
  `self_attn.k_proj`, `self_attn.v_proj`, and `self_attn.out_proj`. Qwen uses
  `o_proj` for its output projection. `[training] lora_targets` chooses the
  placement. `configs/lfm.toml` and `configs/qwen-alllinear-60.toml` use
  `all-linear`, which adapts the feed-forward and convolution layers too.
  `configs/lfm-smoke.toml` stays `attention`, which leaves those layers frozen.
- The native LFM chat template always opens a reasoning block. Screening and
  evaluation therefore retain LFM's native thinking behavior. Qwen's thinking
  toggle is passed only to its own template.
- The tokenizer owns special tokens. The template is tokenized directly to
  avoid adding a second BOS. The closing thinking token is resolved from each
  model's tokenizer.
- LFM and Qwen share one environment and one sampling engine. vLLM serves LFM
  from 0.17.0 onward, where LoRA covers the fused MLP and short convolution.
  The `vllm` extra pins 0.34.0. An older vLLM version stops at startup with the
  required version in the message.
- The one `vllm` extra pins vLLM 0.34.0, torch 2.14.0, Transformers 5.22.2,
  PEFT 0.18.1 and Accelerate 1.8.1. The base model still loads in process for
  the optimizer. The exact install command is in the README.
- The launcher accepts `RLVR_VENV` to select another interpreter, with `.venv`
  as the default. The run root still comes from `--runs-root`.

```bash
python3 -m venv .venv
.venv/bin/pip install -e ".[vllm]" "pytest>=9,<10"
./run.sh code-score --config configs/lfm-smoke.toml --runs-root runs-lfm-smoke
./run.sh code-score --config configs/lfm.toml --runs-root runs-lfm
./run.sh code-score --config configs/lfm.toml --runs-root runs-lfm --resume
```

Model architecture, tokenizer, and supported usage were checked against the
[official model card](https://huggingface.co/LiquidAI/LFM2.5-2.6B),
[pinned configuration](https://huggingface.co/LiquidAI/LFM2.5-2.6B/blob/7141b56cd4650af95c7c7b86983443aed050c96a/config.json),
and [Transformers LFM2 documentation](https://huggingface.co/docs/transformers/model_doc/lfm2).

## Training throughput

Each training step still samples from one policy and applies one optimizer
update after all prompt groups contribute their gradients.

- Docker tests support ordered batches with a configurable worker bound.
  `training.test_workers` defaults to 4. Each container keeps its time limit,
  network isolation, read-only filesystem, PID limit, 256 MiB memory limit,
  and one-CPU limit. The default assumes capacity for four such containers.
- One scoring worker prepares the next already-generated group while the
  training thread backpropagates the current group. Only that thread calls the
  model, accumulates gradients, writes records, or updates weights. The worker
  is joined on completion or failure. `training.prefetch_scoring = false`
  disables overlap for comparison.
- Greedy evaluation generates up to `training.eval_batch_size` questions at
  once, default 8. It halves the batch on CUDA memory exhaustion, preserving
  prompt order and one completion per question.
- Completion log probabilities normalize the completion slice of logits.
  Gradient and old-policy forwards pass `use_cache=False` to avoid retaining
  generation KV state. The thinking-budget logits processor uses tensor
  operations across rows.
- Checkpoint resume restores the adapter into the already loaded model and
  loads the optimizer state from CPU. This avoids loading a second base model
  onto the GPU during resume.

The step metrics include `generation_seconds`, `scoring_seconds`,
`scoring_wait_seconds`, `update_seconds`, `step_seconds`,
`completion_tokens_per_second`, and `sequences_per_second`. Evaluation points
include `evaluation_seconds`.

Scoring and update durations overlap, so their sum can exceed step duration.
These timers measure CPU-visible elapsed time without inserting CUDA
synchronization. Step time spans generation through optimizer update, with
checkpoint, evaluation, and file-writing overhead outside that span. Fake
runs retain deterministic zero timing data.

The dashboard displays phase timings and recent GPU utilization samples,
including the fraction of recent samples at low utilization. Sample windows
and sample counts are shown so sparse observations can be interpreted.

## Robustness fixes

- Resume checks saved arm, model name, model revision, split seed, and run mode
  before changing records. Adapter identity, exact tensor keys, and tensor
  shapes are checked before state is loaded. Missing, unexpected, malformed,
  and truncated adapter tensors are rejected. Record truncation happens after
  successful model loading. Load errors become a clean CLI error.
- Checkpoint discovery skips a manifest whose step differs from its directory.
- CUDA retry restores the prompt cursor and shrinks even a previously settled
  batch. An optimizer allocation failure stops with a checkpoint-resume error
  because an optimizer may already have changed part of its state.
- A new sampling attempt clears partial accumulated gradients.
- Dashboard polling keeps the last valid payload through failed refreshes,
  cancels obsolete requests, times out slow responses, and offers retry.
- Dashboard reads reuse unchanged run payloads. File changes and replacements
  invalidate cached data and trigger fresh file scans. Process state and ages
  refresh independently of unchanged run files.

### Review outcomes

Two independent reviewers checked model/training behavior and dashboard/repo
behavior. The following findings were fixed before publication.

- LFM's bare `out_proj` target also matched convolution projections. Targets
  now include `self_attn`, and the actual hybrid runtime test asserts that
  convolution parameters receive no LoRA adapters.
- PEFT accepted an incomplete adapter state without failing. Resume now
  validates every adapter tensor key and shape before copying values. Runtime
  corruption tests confirm unchanged model values and step after rejection.
- Checkpoint loading errors escaped the CLI's error handler. The CLI now
  reports them cleanly and preserves the existing run records.
- A malformed GPU history could pass refresh validation and crash rendering.
  Nested payload validation and frontend regression checks cover this case.

## Fresh reviewer follow-up

At the user's request, three fresh reviewers independently checked the PR's
training behavior, dashboard/repository changes, and LFM runtime support.
The dashboard and training reviewers found no new actionable issues. Their
checks included 199 dashboard/repository tests, all 21 frontend payload tests,
181 training tests under Transformers 5, and 180 training tests under the
original Qwen stack with one LFM check skipped. The dashboard build reproduced
the committed embedded page.

The LFM reviewer found that the pinned Transformers 5 convolution path treats
left padding differently for a batch and a single sequence. Generation runs
in batches, while old-policy, frozen-reference, and gradient forwards process
individual completions. A nonzero pad embedding could therefore change the
probabilities used to train a padded rollout. A tiny hybrid reproduction showed
a completion log-probability difference of 0.71039. Removing leading pads
matched the batched logits within 4.77e-7 in that reproduction.

LFM cached training entries now remove leading masked tokens and adjust the
prompt length before all three probability forwards. The regression uses
unequal prompt lengths and a nonzero pad embedding to exercise the case that
the earlier zero-pad test omitted. The regression also covers Qwen's padded cache representation.

The corrected full Transformers 5 suite passed 924 tests with 18 Docker checks
skipped locally. The targeted original Qwen runtime passed 71 tests with two
LFM checks skipped. The independent LFM reviewer rechecked all three probability
paths and cleared the finding after 73 passing model/backend tests. The new
regression fails against the pre-fix code with all four compared token log
probabilities differing, including a maximum absolute error of 0.9118.

Full-weight CUDA training and GPU utilization remain unmeasured because the
documented GPU host timed out over SSH.

`scripts/smoke_lfm_vllm.py` proves that vLLM loads a PEFT adapter and swaps it
for another one. It drives `VLLMEngine.set_adapter` with a synthetic adapter,
so it does not prove `VLLMGenerator.apply_update`, the trainer's adapter save,
or an optimizer step. A trainer-driven two-step check on the GPU host would
cover that handoff and is not yet run.
